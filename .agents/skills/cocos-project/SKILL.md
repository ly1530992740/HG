# Cocos 项目 Skill

本仓库是活动中的 Cocos Creator 项目。用户负责框架方向；Agent 在已约定的模块契约内实现业务需求，并在用户要求时参与框架设计。

## 必须遵循的工作流程

1. 阅读 `AGENTS.md`，从 `package.json` 确认引擎版本，检查总体图和目标模块图是否存在；若项目处于设计/架构引导阶段且图表尚未建立，不得新增生产代码，先提出 `PROPOSED` `flowchart`，等待用户批准后建立 `TARGET` 图。
2. 图表存在时，读取 `assets/scripts/MODULE_MAP.md`，再读取受影响模块的 `MODULE_MAP.md`，检查调用方、当前工作区状态和相关测试；不得根据 `CodeBackUp` 或旧代码自行推断目标架构。
3. 将变更归类为业务行为、框架/契约、场景/资源或工具链。业务变更必须放在所属模块内。框架变更必须先说明契约和受影响模块，然后只实现请求所需的内容。
4. 在编辑代码前，必须根据需求和相关模块图向用户说明目标模块、状态所有者、依赖/通信方式、预计文件和图表变化，并用 Mermaid `flowchart` 表达 `当前结构 -> 变更动作 -> 目标结构`。说明中必须明确新增、修改、删除的文件或职责；若图表与代码事实不一致，先报告差异；若涉及框架契约，等待用户确认。
5. 为每个变更行为建立测试映射，列出涉及模块和需要的单元测试、集成测试、场景测试及构建检查，并随行为新增或更新测试。跨模块行为不能只测单个类；涉及 Cocos 运行时的行为必须实际运行场景测试。不得借机扩大到无关重构。
6. 使用项目能提供的最强原生检查验证变更。涉及编辑器的行为，在可用时使用 Cocos 预览/MCP。记录准确结果，并明确区分未执行的检查和失败的检查。
7. 审查最终 diff，检查边界违规、生成文件、缺失的 `.meta` 文件、依赖方向、图表是否需要维护以及未测试的变更行为。

## 不可妥协的边界

- 仓库根目录是唯一活动项目。不得重新创建或依赖 Godot 代码和项目文件。`docs/design-archive/` 只提供历史背景，不是可执行规范。
- 除非用户明确请求框架迁移，否则必须保持 Cocos Creator 3.8.8、项目 UUID、序列化约定和现有资源 UUID 不变。
- 遵循 `docs/architecture/MODULE_BOUNDARIES.md`；不得绕过模块 API，也不得创建跨模块循环依赖。
- 不把“逐行测试”作为目标。要求覆盖行为和分支；纯领域模块目标是 100% 语句覆盖和分支覆盖。任何例外都必须提供证据，并明确留给用户决定。
- 只重复实现、或只断言常量而没有真正执行行为的测试，不算有意义的覆盖。
- 永远不要编辑生成缓存或构建产物。不得修改与当前任务无关的用户变更。

## Cocos MCP 权限

用户授权在本仓库范围内通过已配置的 Cocos MCP 服务进行完整读写编辑器操作：场景、节点、组件、Prefab、Cocos 资源、项目设置、编辑器预览、构建操作、验证、快照和日志。使用完成任务所需的编辑器工具，但必须先检查当前状态，确认并保存变更结果，再进行验证。这项授权不包括仓库外路径、远程发布、Git 提交/推送，也不包括在没有框架任务授权时修改框架契约。

## 文档规则

- 文档必须短小、单一职责；优先更新已有文档，不为同一事实创建第二份说明。
- 架构图统一使用 Mermaid，并明确标注“当前实现”或“目标架构”。静态 import 图不得冒充运行时挂载图。
- 只有在 MCP/编辑器或场景序列化中得到证据后，才能记录节点、组件和生命周期关系。
- 规则写入 Skill，事实写入架构图；不要在业务文档里重复框架规范。

## 架构图维护规则

- `assets/scripts/MODULE_MAP.md` 是总体模块导航图；每个已批准的顶层模块目录维护一份 `MODULE_MAP.md`，说明职责、状态所有者、允许/禁止依赖、公开 API、事件、适配器和测试位置。
- 每次代码、场景或资源变更前必须阅读总体图和受影响模块图。图表是实现导航，不能绕过 `MODULE_BOUNDARIES.md` 或用户批准的架构决策。
- 新增模块、依赖、公共 API、事件、状态所有者或跨模块流程时，必须维护对应总体图、模块图或时序图；只修改模块内部实现细节时不强制改图。
- 图表与代码不一致时，先报告差异和证据。`CURRENT` 只记录已验证事实，`TARGET` 只记录已批准设计，`PROPOSED` 只用于待确认方案。
- `assets/scripts/CodeBackUp/` 只作为旧代码素材库按需检索，不是当前实现，不得直接导入或复制为默认生产代码。
- 设计阶段可以在对话中提出 `PROPOSED` 图，不要求立即落盘；用户批准后才建立对应的 `TARGET` 总图或模块图。没有批准图表时，AI 只能讨论设计、整理需求和检查素材，不能直接新增生产代码。

## 测试闭环与一次性场景

- 变更说明必须写明受影响模块和测试层级。纯领域规则做单元测试；跨模块 API、事件或状态协作做集成测试；涉及 Cocos 组件、节点、Prefab、输入、碰撞、对象池、场景装配或生命周期时做场景测试；影响资源、设置或构建行为时做构建检查。
- 例如新增伤害组件时，应覆盖 Combat 的伤害/生命单元测试、Player 与 Enemy 的攻击和受伤集成测试，以及自动创建玩家和敌人、自动开火、确认命中和受伤结果的场景测试。
- 为单次验证临时创建的场景、脚本、Prefab 和 `.meta` 在验证通过后必须清理；可复用测试基础设施和永久回归测试保留。验证失败时保留临时材料，修复后重新运行并在交付前检查是否有孤儿文件。
